Self-Assessment

During the First Cloud AI Journey (FCAJ) internship at Amazon Web Services Viet Nam Company Limited, from June 15, 2026 to August 14, 2026, I had the opportunity to move from learning AWS as separate services to understanding how those services connect inside a real engineering workflow.

Before the program, my AWS knowledge was still fragmented. I knew some basic concepts, but I had not clearly connected IAM permissions, VPC networking, container deployment, CI/CD, observability and cost control into one complete system. After 9 weeks, I became more confident reading AWS documentation, building a technical report, following workshop-style labs and explaining why a service or design choice fits a specific requirement.

My main contribution in the team project was around CI/CD and GitOps for the DevSecOps Factory on AWS project. I worked with the Jenkins pipeline flow, Docker image build and push process, Amazon ECR, deployment preparation for Amazon ECS Fargate, Argo CD/local GitOps concepts, and the bilingual Hugo report. I also spent significant time cleaning up content, checking references, aligning worklogs with the learning evidence repository and making sure the report did not only look complete, but also made sense technically.

This internship was challenging because many tasks were new to me. There were moments when I had to reread the same AWS documentation many times, compare workshop instructions with my own implementation notes and ask myself whether I really understood the reason behind a configuration. That process was not always fast, but it helped me build a more practical learning habit: read, test, document, review, then improve.

Strengths

  • Consistent learning attitude: I did not understand every topic immediately, but I kept returning to the material until I could explain it in my own words.
  • Documentation mindset: I became more careful with evidence, references, file structure, screenshots and bilingual consistency.
  • Technical foundation growth: I now have a clearer mental map of how IAM, networking, containers, pipelines, monitoring and cost control fit together.
  • Willingness to revise: I learned that a report is not only about filling pages. It must be technically correct, natural to read and honest about the work done.

Areas for Improvement

  • Presentation confidence: I need to practice explaining architecture decisions out loud, especially when asked follow-up questions.
  • Deeper troubleshooting: I can handle smaller issues, but I still need more experience with root cause analysis for distributed systems and production-like failures.
  • Time management: I should document labs and lessons immediately after finishing them, instead of waiting until the end of a week.
  • Architecture trade-off thinking: I want to improve the habit of comparing multiple options by cost, security, reliability and operational effort before choosing one.

Personal Reflection

The biggest change for me after FCAJ is that I no longer see AWS as a list of services to memorize. I started to see AWS as a set of building blocks that must be selected carefully depending on context. For example, choosing ECS Fargate is not only about running containers; it also relates to cost, deployment workflow, IAM roles, image registry, monitoring and cleanup.

I also realized that technical growth is not only measured by how many tools I can name. It is measured by whether I can read a requirement, identify the constraints, build something small, explain the trade-offs and document the result clearly enough for another person to follow.

Next Development Plan

  • Review AWS fundamentals regularly through AWS Skill Builder, AWS Study Group workshops and certification-style questions.
  • Continue improving the DevSecOps Factory project by cleaning up pipeline scripts, documentation and monitoring notes.
  • Practice public speaking by presenting one AWS topic at a time in a short and simple format.
  • Strengthen hands-on skills in IAM, VPC, ECS Fargate, CloudWatch, CI/CD security scanning and cost optimization.
  • Keep the habit of writing personal technical notes after each lab so future reports and projects are based on real evidence, not memory alone.
